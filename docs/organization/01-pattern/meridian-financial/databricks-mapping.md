## 2. Prerequisite status: NOT yet landed

`5.2-create-unity-catalog`'s catalogs use the single default `databricks` provider, which targets
exactly one workspace's Terraform state at a time. Today, that one workspace is
`workshop-workspace`, already holding the unrelated `analytics` catalog. **None of the 18
workspaces above can have Terraform-managed catalogs yet** — realizing more than one of them
(and this org needs 18) requires a one-time extension to `05`: a distinct, aliased `databricks`
provider per workspace, plus catalog/schema/group/grant resource wiring against each alias.

This is a **blocking engineering prerequisite**, not a per-catalog decision — every catalog line
in Section 3 below is planned-only until it lands. (Once a catalog exists, it's visible/grantable
from any workspace on the same metastore regardless of which workspace's state created it — the
limitation is about *which Terraform state can create it*, not about runtime access.)

## 6. Constraints carried forward from `05`

- **Prerequisite not yet landed** (Section 2) — every catalog in Section 3 is planned-only until
  `05` gets its provider-per-workspace extension.
- **`5.3` does not grant workspace login access itself** — every `acl_*` group above (81 of them)
  still needs a separate workspace-permission-assignment step this project's Terraform doesn't
  cover yet.
- **`abac` (row/column masking) is reserved vocabulary, not implemented** — the retail/institutional
  PII gaps stay open regardless of workspace strategy.
- **This project's `05` skills are AWS-only** — `org-structure.yaml` scoped this org to AWS/
  `us-east-1`, consistent with that.
- **18 workspaces is a genuinely large real-cost commitment** — confirm this is actually wanted at
  full scale before `6.3` turns this into a plan with 18 real `5.1` runs; scoping down to a subset
  (e.g. one BU end-to-end first) is a legitimate alternative to raise with the user, even though
  the canonical *pattern* itself isn't up for renegotiation.
