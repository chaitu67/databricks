# Databricks mapping: northwind-financial

Generated by `6.2-map-databricks-pattern` from [`org-structure.yaml`](org-structure.yaml).

## 1. Pattern used

**[01-pattern](../pattern-definition.md)** — one workspace per business unit/department ×
environment tier; a line of business (LOB) is a catalog inside its unit's workspace. Fits this
org: no shared-workspace requirement or different catalog granularity was stated in
`org-structure.yaml`, and its shape (BUs with LOB splits, shared departments needing cross-BU
read access) matches `01-pattern` directly — same as `meridian-financial`, the pattern's other
instance.

Realized by `infrastructure/modules/organization/01-pattern` (self-contained per-unit provider),
scaffolded per unit via `infrastructure/scripts/add-pattern01-unit.sh`. This mechanism is already
built and validated (see `01-pattern/pattern-definition.md` — Status) — unlike when
`meridian-financial` was first mapped, there is no outstanding engineering prerequisite blocking
any of the catalogs below.

### 2a. DR standby workspaces (us-west-2, workspace-only)

`org-structure.yaml`'s `dr` block requests a standby in **us-west-2** for the `prod` tier.
Since Unity Catalog metastores are region-bound, a `us-west-2` workspace can't share
`us-east-1`'s catalogs — per the stated scope ("workspace only, data replication is separate"),
these standbys get **no catalogs through this pipeline, permanently** (not the ordinary
two-phase "catalogs follow later" case). Applies to every unit with a `prod` tier — both BUs and
shared departments, since the DR requirement wasn't narrowed to a subset.

## 4. Cross-BU grants (shared departments reading across units)

Each department below is **one group per catalog it owns**, granted **read-only** on every LOB
catalog of the BUs in its stated `scope`, matching each department's own environment tiers to the
target BU's matching tier (a department doesn't reach into a tier it doesn't itself operate in).
Realized via `01-pattern`'s `extra_grants` mechanism — an input on the *target* catalog's own
unit, not a standalone resource (see `pattern-definition.md`).

**Assumption, not stated in `org-structure.yaml`: read-only access.** None of the three
departments' access *level* was specified during discovery — only their environment tiers and
BU scope. Defaulting to `reader` for all cross-BU grants (matching how `meridian-financial`'s
compliance/finance departments were modeled) since these are cross-cutting oversight/reporting
functions, not data-producing ones. **Confirm this is correct before treating the plan as final**
— if any department needs write access to another BU's catalog, that changes the grant's
privilege set.

## 6. Constraints carried forward from `01-pattern`

- **Two-phase requirement for every one of the 14 catalog-bearing units** (all brand new) — each
  unit's workspace must be created and confirmed `RUNNING` before its catalogs can be added, since
  the catalog's provider needs the workspace's real, Databricks-assigned URL. See
  `pattern-definition.md` / `6.4-deploy-organization`'s "two-phase reality." The 6 DR standby
  workspaces (Section 2a) never reach a catalogs phase at all — they stay workspace-only
  permanently, by design.
- **No volume support, no workspace-login/permission assignment for the groups created, no
  row/column masking** — same gaps as `01-pattern`'s other instance; not relevant to the
  masking gap specifically here since no PII was flagged, but the login-assignment gap still
  applies to all 66 groups.
- **This project's automation is AWS-only** — consistent with `org-structure.yaml` scoping this
  org to `us-east-1`/`us-west-2`.
- **20 workspaces (14 + 6 DR) is a genuinely large real-cost commitment** — confirm this is wanted
  at full scale before `6.3` turns this into a plan with 20 real workspace creations; scoping down
  (e.g. one BU end-to-end first, or deferring the DR standbys) is a legitimate alternative to
  raise with the user.
